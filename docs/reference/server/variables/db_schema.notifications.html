    Notification records — the messages the system has decided to send (REQ-F-005).

    A row is written by the operation that causes the message, in the same transaction that causes it, so a booking and its confirmation message are created together or not at all. At S2.2 that is the booking transaction in modules/appointments/service.ts; S2.3 (cancellation), S3.1 (reschedule) and S4.1 (preferences) add their own rows through the same table.

    sent means "handed to the simulated channel", not "delivered to a phone". SMS delivery is simulated in this version (SRS §3, Assumptions and Dependencies), so the record states the system's decision, and sent_at is the instant it was made.

    The partial unique index is decision E4, and it is the backstop that makes REQ-F-005 "exactly one" rather than "at least one". One appointment can have at most one client/new/sms record; a second insert fails at the database. It is partial on those three predicates because a second reschedule must send a second SMS with event_type = 'reschedule' (REQ-F-009), and a full unique on the four columns would forbid it.

    scheduled_at is nullable: a record written now (status sent) has no future moment. The reminder engine (SMS-29) writes scheduled rows with it set.

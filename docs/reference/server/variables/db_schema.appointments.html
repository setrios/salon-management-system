    Appointments (REQ-F-001, REQ-F-003, REQ-F-031).

    start_at and end_at are instants, not wall clock: an appointment names a moment, and the salon's zone is applied when it is built (lib/time.ts). end_at is start_at plus the occupied block, not the summed duration — REQ-F-031 rounds the block up to 30 minutes, and the reserved time is what a conflicting booking must be compared against.

    status starts at confirmed (REQ-F-003: there is no approval state) and is constrained to the three values the contract's Appointment.status enum names. The constraint is the schema's, not a route's: S2.3 and S3.1 add the transitions, and neither may invent a fourth value.

    The partial unique index is decision D2, and it is half of the concurrency answer. Two simultaneous requests for the same start must not both insert; the index makes the second one a database-level failure. It is partial on status <> 'cancelled' because a cancelled appointment frees its block: a later booking at the same instant is legitimate, and a plain unique index would refuse it forever. The other half — the overlap the index cannot see — is pg_advisory_xact_lock(master_id) in modules/appointments/service.ts.

    access_token is the client's credential (REQ-NF-001, REQ-F-004). It is generated by the database so two concurrent bookings cannot collide on it, and it is unique for the same reason. confirmationUrl is derived from it, not stored: the base URL is a deployment fact, not a property of a booking.

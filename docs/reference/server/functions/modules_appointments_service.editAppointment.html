    Function editAppointment

    • editAppointment(
          input: AppointmentEditInput,
          recheck: (tx: Executor) => Promise<boolean>,
      ): Promise<AppointmentEditResult>

      An edit — P11's reschedule and R21's administrator patch — inside one transaction.

      One write for both operations (K3): P11 and R21 differ in what they decided, not in what the write does, so a second copy of this transaction would be a second place for the reminder recalculation, the guarded update and the event rows to drift.

      The advisory lock is on the new master (D2, G5), taken before the caller's recheck runs. A reschedule takes a block on the new master's calendar, so it is the same check-then-write race P8 has, and the same lock answers it. The partial unique index appointments_master_start_unique is the backstop for the exact-start race, and its violation is mapped to slot-unavailable, not left to the 500 branch.

      The update is guarded by status = 'confirmed' (the same precondition state.ts names for edit). The state was checked before the transaction; the guard is what makes a concurrent cancel or complete win cleanly — zero rows, and the route answers 409 rather than writing over the winner.

      The reschedule row is written here, not after the commit (G6, the same reasoning as E2 for the confirmation): one transaction, one commit, or neither. There is no unique index for it, because REQ-F-007 allows any number of reschedules (R17). R21 writes it only for a time or master change (K4, L4) and passes its own actor, so REQ-F-030 suppresses the administrator's row.

      The lines are re-priced only when the master changed (G8); when R21 also names a service set, replaceLines rewrites the rows instead (L4).

      The reminder rows are recalculated in the same transaction (H6) when the time moved: the new startAt moves both moments, and a moment that is now past is skipped rather than left scheduled for a dispatch that would never come. An edit that keeps the time (a master, service-set or client change) leaves them alone.

      The re-read is findById after the transaction commits, so it sees the committed row; reading inside the transaction through the pool would be a second connection and would not see the uncommitted update.

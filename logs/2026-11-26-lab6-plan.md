The lab closes the SDD cycle: the code is brought to an agreed convention, the
system is documented as it actually is, the documentation is checked against
the code and the interface, the traceability matrix is completed and audited,
and the system is validated by the human against `spec/DESCRIPTION.md`.

## 3. Decisions

| ID | Decision | Reason |
|---|---|---|
| D-L6-1 | **The UI is built in this lab, as stage S6, before the documentation stages.** No addendum: SMS-36 is a ticket of the plan approved at PLAN-GATE, and the interface is required by the approved SRS. | The lab's premise is that documentation describes functionality that has passed its checks; step 10 checks the user guide against the actual UI; FINAL-GATE asks the human to confirm fit to `DESCRIPTION.md`, which names the confirmation page with cancel / reschedule links. Deferring the UI would have been a legitimate addendum under time pressure; there is none. |
| D-L6-2 | UI technology: static pages, TypeScript without a framework, compiled by the project's `tsc`, served by the same Express process; it calls only the approved `/api/v1` contract. | No new runtime dependency; one language and one build; the UI is one more client of the API-GATE contract, which stays unchanged. |
| D-L6-3 | UI screens are specified in `spec/ui/screens.md`, each screen traced to REQ-IDs and API operations, and approved at a **UI-GATE** before any UI test is written. | The same order as API-first in lab 4: the interface is derived from requirements, and the decision is the human's. |
| D-L6-4 | UI tests are browser end-to-end tests (Playwright), derived from SCN-01…SCN-16 and the acceptance criteria of REQ-NF-002/003/004/006/007; REQ-NF-002 is checked on a mobile viewport. | REQ-NF-002's criterion ("usable without horizontal scrolling") cannot be checked by an HTTP test. |
| D-L6-5 | Coding convention: Google TypeScript Style Guide as the base, adapted to the project; enforced by ESLint (typescript-eslint, `naming-convention`, `eslint-plugin-jsdoc`) and Prettier. The convention is set **before** stage S6, so the UI is written to it. | A recognised style for the language (step 1); a linter turns "the code follows the convention" into a report (step 2). |
| D-L6-6 | References: Redocly HTML from `openapi.yaml` (the lab 4 contract) and TypeDoc from the TSDoc comments. | Step 5 asks to update the lab 4 API reference; TypeDoc also reports undocumented exports (steps 4, 9). |
| D-L6-7 | FINAL-GATE of lab 6 is its own ticket (SMS-68) and its own record; the lab 5 record stays as it is. | Different decision, different scope. |
| D-L6-8 | The final version is the annotated tag `v1.0.0`; `package.json` goes from 0.1.0 to 1.0.0 in the same stage. | One tag that names one version (step 17); the developer pushes it. |
| D-L6-9 | SMS-49 is labelled `type: feature`, as SMS-46 (the earlier refactoring) is. | Consistency with the tracker; no label for one ticket. |

## 2. GitHub Issues setup

- **Repository issues** act as tickets; issue numbers are sequential, and
  because issues are created in exact plan order, **issue #N = plan ticket
  SMS-N** — the same ID everywhere.
- **States:** GitHub has only open/closed, so the 4-state workflow is
  carried by labels (the issue timeline provides the change history the
  process requires):

| State | Representation | Meaning |
|---|---|---|
| `Backlog` | label `status: backlog` | Accepted, not started (не виконана) |
| `In Progress` | label `status: in progress` | Active work (активна) |
| `In Review` | label `status: in review` | Written, awaiting verification/validation (перевірювана) |
| `Done` | **issue closed** | Accepted (завершена) |
| `Blocked` | label `status: blocked` | Waiting on a dependency or a gate decision |

- **Type** (label `type: …`, 8 values — the SDD cycle):

| Type | Produces code? | Produces test? | Primary owner |
|---|:---:|:---:|---|
| `Specification` | no | no | Human |
| `Addendum` | no | no | Human — new functionality only via spec revision |
| `Test` | no | yes | Agent drafts, human reviews |
| `Feature` | yes | no | Agent implements |
| `Verification` | no | no | Agent runs checks, human signs off |
| `Validation` | no | no | **Human only** |
| `Documentation` | no | no | Agent drafts, human reviews |
| `Gate` | no | no | **Human only** — allows/blocks a stage transition, produces no code or test |

- **Assignee role** (label `role: …`): `Coding Agent` / `Human` / `Joint`.
- **Dependencies:** each issue body contains `Blocked by #N` lines — GitHub
  auto-links these as cross-references in both timelines; the blocking
  relation is stated in the body text (`Blocked by #N` on the dependent).
- **Source:** requirement/scenario IDs are stated in each issue body
  (e.g. `Source: REQ-F-007, REQ-F-008, SCN-03`).

## 3. Workflow (state transitions and permitted roles)

| Transition | Permitted roles | Condition |
|---|---|---|
| Backlog → In Progress | Agent or Human | Ticket's TEST ticket exists (test-first); no unmet blocking dependency or pending gate |
| In Progress → In Review | Agent | Work complete; paired TEST ticket Done; agent self-check performed |
| In Review → Done | **Human only** | Verification passed / validation or gate sign-off |
| In Review → In Progress | Human only | Changes requested |
| In Progress → Blocked | Agent or Human | Dependency/gate/clarification missing |
| Blocked → Backlog | Agent or Human | Blocker resolved |

Hard rules: the agent never moves a ticket into `Done`; Validation and Gate
tickets are executed and closed by the human only.

### Task lifecycle diagram (roles on transitions)

```
                   create / accept
       +---------+ --------------------------> +-------------+
       | BACKLOG |    [Human / Agent]          | IN PROGRESS |
       +---------+ <-------------------------- +-------------+
            ^          block / unblock               |
            |           [Human / Agent]              | submit for review
            |                                         | [Agent]
            | rework: changes                         v
            | requested              +-----------------------------+
            | [Human]                | IN REVIEW                   |
            |                        | (verification / validation) |
            |                        +-----------------------------+
            |                              |                  ^
            |                              | approve:         | rework:
            |                              | sign-off / gate  | changes requested
            |                              v                  | [Human]          
            |                        +----------------+       |
            +----------------------- |      DONE      | ------+
              [Human]                +----------------+
```

Transition ownership summary: the agent may start work and submit for
review; only the human approves into `Done`, requests rework, and
executes Validation and Gate transitions. Both roles may set/clear
`Blocked`.

### Gantt-style schedule (stages as bars, gates as diamonds, critical path marked)

Durations are orientive working days; bar length is proportional. `====`
marks the critical path (plan §7). No calendar dates — set at PLAN-GATE.

```
Stage                0d   1d    2d    3d    4d    5d    6d    7d    8d    9d   10d
S0 Setup            |##|                                                    
  PLAN-GATE            ◆--  (0.5 d, human)                                   
S1 Foundations       CRIT |=====|=====|=====|     G1 ◆                        
S2 Booking core              CRIT |=====|=====|=====|     G2 ◆                  
S3 Resched+remind                                CRIT |=====|=====|              
S4 Notif+master view                                   |=====|=====|     G3 ◆      
S5 Admin+payment                                            CRIT|=====|=====|== G4 ◆
S6 NFR+final                                                       |=====|=== FINAL VAL
```

Reading: `◆` = gate decision (human-only); `CRIT` prefix = stage contains
critical-path tickets. Human validation windows are nested inside each
stage's tail; if a review slips, everything to its right slips with it.

**Human-action durations (assessed separately, per the process requirement):**
gate reviews 0.5–1 h each; validation per stage 1–2 h; ticket triage ~0.25 h
per ticket; traceability upkeep 0.5 h per stage. Total human effort ≈ 4–6
working days spread across the plan. These windows, not the agent's coding
speed, are the throughput constraint: if the human defers a review or a
gate decision, all dependent stages slip.

## 7. Critical path (determined manually, justified)

SMS-23 → SMS-24 → SMS-25 → SMS-26 → SMS-28 → SMS-29 → SMS-32 → SMS-34 → G4 →
final validation.

Justification: booking correctness (SMS-25) gates every downstream flow;
reschedule logic (SMS-28) is reused by admin edits (SMS-32); payment (SMS-34)
sits at the end of the longest chain because completion (REQ-F-027) must
precede it. A delay in any of these tickets delays the project end date
directly. Notification (SMS-30) and reports (SMS-35) have slack and are not
on the critical path.

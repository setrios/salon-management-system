## 1. Scope

S4.1 delivers three operations and the service behind them:

| Operation | Method and path | What it does |
|---|---|---|
| M5 `getMyNotificationPreferences` | `GET /me/notification-preferences` | the caller's six channel × event settings |
| M6 `updateMyNotificationPreference` | `PATCH /me/notification-preferences` | toggles exactly one of them |
| M7 `listMyNotifications` | `GET /me/notifications` | the caller's own notification records, filtered and paged |

and the rule that makes the settings mean something: **an appointment event
writes one row per enabled channel, for the master and for the administrator**
(REQ-F-016, REQ-F-023).

**What this stage does not deliver: the acting-administrator suppression
(REQ-F-030).** SCN-12's "When" is R21 — the administrator's cancellation — and
R21 is S5.1. A rule with no operation to drive it cannot be asserted over HTTP,
and the plan puts S4.1 before S5.1. SMS-18 therefore moves to S5.1, which adds
the actor and the suppression with its own test. §5 records the carry-forward;
§8.3 criterion 6 of the plan is what sanctions it.

### 1.1 The inventory (I1–I11)

**I1 — a preference is a stored row keyed by the principal.** The principal is
a `masters` row: the administrator is one, with `role = 'admin'` (REQ-F-017), so
one table serves both roles. The alternative — a separate `admin_preferences`
table — would duplicate the six combinations for a single account.

**I2 — the table is a sparse override, and enabled is the default.** A row
exists only for a combination the caller has toggled; M5 answers all six,
filling the missing ones with `enabled: true`. Enabled is the default because
REQ-F-016's AC speaks of *disabling* a channel: a default of disabled would mean
no notification is ever sent, and the AC would be satisfied vacuously.

The order M5 answers in is fixed — sms/new, sms/reschedule, sms/cancellation,
in_app/new, in_app/reschedule, in_app/cancellation — so a client can diff two
answers. The contract does not pin an order; this stage does, and P1 asserts it.

**I3 — M5, M6 and M7 are `JWT`, not `JWT-M`.** The contract declares no 403 for
any of them, unlike `/me/availability`, `/me/appointments` and `/me/services`,
which do. The administrator has preferences and rows of their own (REQ-F-023),
so one pair of operations serves both roles. P9 and N2 are what make that
observable.

**I4 — M6 is an upsert of exactly one combination.** The same body twice leaves
one row and the same answer (P3). A body that violates
`NotificationPreferencePatch` is 422 `VALIDATION_ERROR` (M6 declares 422); a body
that is not JSON is 400 `MALFORMED_REQUEST` (CL-09's rule: the operation's own
response set decides, not the operation id).

**I5 — an event writes one row per enabled channel.** A disabled channel writes
no row at all. That is REQ-F-016's AC read literally, and it is why the rows are
written per preference rather than written and filtered on read: a row that
exists is a message that was handed to the channel.

**I6 — the administrator's row is suppressed when the administrator caused the
event.** Not in this stage; see above and §5.

**I7 — the client's own rows are not governed by preferences.** The confirmation
SMS (E2) and the two reminders (H1) are written whatever the master's settings
say. REQ-F-016 is about the master's notifications, and P12 asserts the contrast
on one event: the master's SMS off, the client's on.

**I8 — a row written for a master or the administrator is `sent` with `sentAt` =
the event's clock.** The channel is simulated (E3); there is no queue for the
row to be `scheduled` in, and `scheduledAt` stays null.

**I9 — "the caller's rows" is derived, not stored.** The `notifications` table
carries no principal column. For a master, M7 answers the `audience = 'master'`
rows of appointments assigned to them; for the administrator, the
`audience = 'admin'` rows. The appointment already names the master, so a column
would be a second copy of the same fact.

**I10 — `from` and `to` filter on `createdAt`, inclusive of the whole day.**
`scheduledAt` is null for the confirmation and the reschedule rows, so it cannot
be the filter's column; `createdAt` is the only one every row has.

**I11 — the order is `createdAt` then `id`, the same as R24's**, so a page is
stable across calls.

### 1.2 The consequence the register must carry

With enabled as the default, a client booking now writes **four** rows beyond
the ones S2.2 and S3.2 wrote: `new`/`master`/`sms`, `new`/`master`/`in_app`,
`new`/`admin`/`sms`, `new`/`admin`/`in_app`. A reschedule and a cancellation add
the same four for their event type.

That changes what R24's `total` counts, and five assertions in
`tests/api/reschedule.test.ts` were written against the old count (4, 5, 4, 3,
3). They are re-stated in `25de209` (§1.5) to count the **client's** rows by
predicate — the same treatment `tests/api/notification.test.ts` already uses for
REQ-F-005 — because "the reschedule wrote exactly one row" is a statement about
the client's message, not about the page's size.

### 1.5 Four test corrections after the gate was signed

GREEN exposed four assertions written against the pre-S4.1 row set. Each is a
correction to a test, not to the code, and each is in `25de209`.

**K6 (`cancellation.test.ts`) asserted that a cancellation writes no row for
*any* audience.** Its own comment said why that was a stage-scoped reading:
"neither has a preference or an actor to consult yet". S4.1 is the stage that
gives them one, so the case now asserts the client's absence only — which is
what SRS v1.3 lines 253–256 actually say — and the other two audiences'
presence is asserted in `notification-preferences.test.ts` (P10–P13).

**The five `reschedule.test.ts` totals counted the whole page.** With the
master's and the administrator's rows on it, 4 became 12 and 5 became 17. They
now count the client's rows by predicate, which is what "the reschedule wrote
exactly one row" was always about; the numbers are the same as before (4, 5, 4,
3, 3), so the assertion's meaning is unchanged and only its scope is stated.

**R17's `reschedule` filter matched every audience.** It now requires
`audience = 'client'`, for the same reason: the master's and the administrator's
`reschedule` rows are on the same page.

**N5 assumed `createdAt` is the injected clock.** It is not: the column is
`defaultNow()`, so the row carries the database's clock, not `app.locals.now`.
The case now reads the date back from the row it is filtering on, which is what
makes it a test of the filter rather than of the clock.

### 1.6 Two shared changes the stage needed

`coerce` in `src/middleware/validate.ts` now rejects a query value outside its
schema's `enum`. M7 is the first implemented operation with an enum query
parameter (`status`, `eventType`), and without the check `?status=bogus` would
have been a filter that matches nothing rather than the 400 the contract
declares. No earlier operation has an enum query parameter — the other six are
on M1, R20, R25, R28 and R29, none of which is implemented yet — so the change
alters no existing behaviour.

`addCalendarDays` in `src/lib/time.ts` is the other addition: `to` is inclusive
of the whole day, and the next midnight is a calendar increment, not 24 hours
(I10).

## 3. Where the rows are written

One function, `recordAppointmentEvent(executor, { appointmentId, eventType,
actor, now })`, called from the three client paths:

| Caller | Event | Actor |
|---|---|---|
| P8 `createAppointment` | `new` | `client` |
| P10 `cancelByToken` | `cancellation` | `client` |
| P11 `rescheduleAppointment` | `reschedule` | `client` |

It reads the appointment's master, reads the master's and the administrator's
preferences, and inserts one row per enabled channel for each. It runs inside
the caller's transaction, so a booking that fails writes no notification.

`actor` is a parameter from the start even though S4.1 only ever passes
`client`: S5.1's paths pass `admin`, and the parameter is what makes the
suppression a property of the service rather than of each route.

### 6.1 Three cases were fallback-green and were corrected before the gate

A case that passes at RED proves nothing. Three did, and each was rewritten:

- **P6** (400 for a malformed body) passed because the JSON parser rejects the
  body before routing, so a 404 route still answers 400. It now first asserts
  that a valid body on the same route is 200, which is what makes the 400 M6's.
- **P11** (no master row when both channels are off) passed because at RED no
  master row is written for any reason. It now also asserts that the
  administrator's two rows are there, so the empty master list is a suppression
  and not a booking that wrote nothing.
- **P12** (the client's SMS is unaffected) passed because the client's row is
  written by S2.2 and the case only looked at it. It now asserts the contrast on
  the same event: the master's SMS off, the client's on.

A fourth correction was mechanical: the row comparisons used `toEqual` against
four-field objects while R24 returns nine, so they would have failed after GREEN
for the wrong reason. They now project the four fields first.

### 1.1 R24 is in this stage — and the plan says nothing about it

assigns REQ-F-005 to ticket **SMS-26**. `docs/ticket-list.md:43` gives SMS-26 its

**The implementation plan has no stage for R24.** `logs/2026-11-08-implementation-plan.md`

REQ-F-023, REQ-F-026, REQ-F-030) is REQ-F-005. Without R24 in S2.2, REQ-F-005's
"exactly one is recorded" has no API surface until whichever later stage notices.

This gate closes that gap by putting R24 in S2.2. It does **not** edit the plan;
the plan revision that records it is a G2 matter, like every other plan

**Alternative not taken:** P9 only, with "exactly one" asserted by reading the
`notifications` table directly from the test. Rejected because it makes the test

and because it would leave a requirement in the SRS matrix owned by a ticket that

## 4. Decisions this gate records

E1–E10 are the inventory's decisions, recorded in `tdd-SMS-26.md` §5 with the
alternatives. The gate restates the three that change behaviour, and the one that
bounds what "sent" may claim.

### 4.1 E2/E4 — the message is a row written in the booking transaction

One successful `POST /appointments` inserts one `notifications` row in the same
transaction as the appointment and its lines, under the same
`pg_advisory_xact_lock(master_id)` (D2). A failed transaction writes none. The
partial unique index on `(appointment_id) where event_type='new' and
audience='client' and channel='sms'` is the backstop, in the shape of D2.

**Alternative not taken:** computing the message on read, as `reminders` are
computed (D6). REQ-F-005 says "is recorded"; a computed value cannot be "exactly
one record", and a rolled-back booking would leave a trace.

**Why the index is partial on those four predicates and not a full unique on the
four columns:** a second reschedule of the same appointment must send a second
SMS with `eventType: reschedule` (REQ-F-009). A full unique would forbid it.

### 4.2 E3 — `status: sent` means "handed to the simulated channel"

SMS delivery is simulated in this version (SRS §3, Assumptions and Dependencies:
"SMS sending is simulated"). The record's `sent` therefore states that the system
decided to send the message and gave it to that channel — **not** that it reached
a phone. No test and no document may read it as delivery. The real dispatch
statuses belong to the reminder/notification engine (SMS-29, SMS-30).

### 4.3 E7 — the token stays valid after cancellation

SRS v1.3 glossary, "Confirmation Page": "The page and its access token remain
valid after cancellation: the page then shows status `cancelled` and the
cancel/reschedule controls are disabled rather than the link being invalidated."
C8 asserts 200 with the same token and `confirmationUrl`. The `cancelled` state is
arranged out of band because P10 is S2.3; C8's header says so. The arrangement is
replaced by P10's own call when S2.3 lands.

### 4.4 E9 — a `startAt` in the past stays open, and its decision point is G2

P8 currently accepts a start in the past. From S2.2 that produces a recorded
confirmation message for a visit that cannot happen — though the delivery is
simulated, so the effect is a record, not a call. No document defines "past"
(`now`, start of day, DST edge), and changing P8 would edit the signed S2.1 stage
outside its gate.

**Carried to the G2 register (§5 row 4) with a named decision point: the human,
at G2.** At G2 it is either closed (candidate answer: 422 `BUSINESS_RULE_VIOLATION`
on P8, which P8 declares) or carried again with a new reason. A silent "deferred
again" is not an option: the row records who decides and where.

### 4.5 E5/E10 — what the contract cannot express

- `confirmationUrl` is built from the contract's example origin
  (`https://salon.example`) and nothing serves it. S2.2 does not change that; C6
  asserts only that the URL a client received at booking is the URL a later read
  returns. Whether the page is *served* at that URL is SMS-36's UI work and a
  register row.
- `Notification` has no text field. "Containing a valid link to REQ-F-004's page"
  is not representable; the record links by `appointmentId`, and the link itself
  is `Appointment.confirmationUrl` (B7, C6). Adding a text field is an addendum
  candidate (SMS-45), not a change made here.

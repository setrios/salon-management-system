The inventory's C1 was *"lists an active service with its duration and category,

authority, not the plan's.

## 4. Decisions this gate records

Three decisions are the gate's own — the rest (D1–D7, D11) are read from the
contract or were taken earlier and are recorded in `tdd-SMS-25.md` §5.

### 4.1 D8 — a repeated service id is counted twice

`AppointmentCreate.serviceIds` declares `minItems: 1`, `maxItems: 20` and **no
`uniqueItems`**. A body with the same id twice is therefore permitted by the
contract, and REQ-F-001 says the total is "the sum of the selected services", read
literally. B24 asserts two lines, doubled duration and doubled price.

**Alternative not taken:** de-duplicating the ids. It would be a rule the contract
does not state, applied to a body the contract permits — the same shape as the
unwritten rules CL-10 exists to keep out.

### 4.2 D9 — the clock is injected

`createApp({ now })` takes an optional function returning the current instant,
defaulting to `() => new Date()`. Reminder status depends on "now" (REQ-F-010,
REQ-F-011), and B9–B11 fix it, so the file behaves identically on any day it runs.

**Alternatives not taken:** fake timers (they would have to intercept the
driver's and the framework's timers as well, and a leak would make the suite
order-dependent); no injection (the reminder cases would then be true only on
some days, which is the defect `--sequence.shuffle` found at S1.2 in a different
guise).

**Consequence for GREEN, stated plainly:** Vitest does not type-check. A green run
proves the assertions hold, not that the code compiles. At RED, `tsc --noEmit`
reports three `TS2554` on `createApp({ now })` — that is the proof D9 is not
implemented. The GREEN evidence must therefore include a **separate clean
`tsc --noEmit`**, and "the tests are green" is not a substitute for it.

### 4.3 D10 — the public surface is bookable masters only

The administrator is a row of `masters` with `role = 'admin'` (D-19). Without a
decision, P4 would list the administrator as a bookable master. P4 lists
`role = 'master'`; P5 and P6 answer 404 for an administrator id, the same answer
they give any id that names no bookable master. C14, C19 and C24 assert it; C15
carries a guard, not a proof — see §1.2.

**Alternatives not taken:** listing every row (offers the administrator for
booking); 403 for an administrator id (not declared on a public operation, and it
would confirm the id exists).

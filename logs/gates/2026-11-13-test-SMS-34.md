## 1. Scope

S5.3 delivers the one operation that records money, and the field that shows it:

| Operation | Method and path | What it does |
|---|---|---|
| R27 `createPayment` | `POST /admin/appointments/{appointmentId}/payments` | records a `paid` or `unpaid` payment of a **completed** appointment, once; answers 201 `Payment` |
| — (field) | `AppointmentAdmin.payment` | R20, R21–R23 and `getAppointmentAdmin` expose the recorded payment when there is one |

The precondition is REQ-F-027's ("a precondition for payment"): the appointment
must already be `completed`, which R23 (S5.1b) sets. The cardinality is D12's:
at most one payment per appointment, immutable.

### 1.1 The inventory (N1–N8)

| # | Decision | Where it is asserted |
|---|---|---|
| N1 | **Any amount is accepted**, including a value above the appointment's `totalPrice` and the contract's minimum of `0`. REQ-F-021 says the administrator records the amount; nothing states equality with the total, and inventing that refusal would be a rule the SRS does not carry. The absence of the rule is asserted, not merely documented. | P7 |
| N2 | **`payment` is returned in the staff representation** once recorded, and is *absent* (not `null`) when there is none — the property is optional in `AppointmentAdmin`. Without it the only evidence of a payment is a second request's 409. | P1, P4, P6, P10 |
| N3 | **No `Location` on the 201**, for the reason R26 gives (M5): no operation reads one payment, so the URI would name something unfetchable. The contract declares the header, not its presence. | P1 |
| N4 | `status` defaults to `paid` when the body omits it (the contract's `default: paid`); `unpaid` is accepted and echoed. The payment row is the record of what was agreed, not a gateway result (REQ-NF-009). | P2, P3 |
| N5 | **The two 409s have an order**: an appointment not `completed` answers `APPOINTMENT_NOT_COMPLETED` first; a second payment on a completed one answers `PAYMENT_ALREADY_RECORDED`. They cannot overlap — a payment requires `completed`, and a `completed` appointment can no longer be cancelled (R22) — so the order is a reading, not a race. | P4, P5, P6 |
| N6 | Recording a payment **does not write the appointment row**: its `status` stays `completed` and its `updatedAt` does not move. The payment is its own table and its own response. | P1, P10 |
| N7 | `notificationsSummary` stays out of scope; it is optional in `AppointmentAdmin` and no stage has claimed it. | §1.2 |
| N8 | The table is `payments` (migration 0007), with `appointment_id` unique — D12 enforced by the schema, not only by the handler — `amount_minor` integer, `currency`, `status`, `method`, `recorded_at`. | P6, P10 |

### 1.2 What the stage does not deliver

- **`notificationsSummary`** (N7).
- **`422 BUSINESS_RULE_VIOLATION` on R27.** `error-model.md` §3 lists R27 in that
  row's examples, but no reachable trigger is defined for it: D12 is a 409
  (`PAYMENT_ALREADY_RECORDED`), the state rule is a 409, and the body's mistakes
  are 422 `VALIDATION_ERROR` (D22). It is recorded here as an unreachable
  declared outcome, as the S1.2 gate did for 409 on R4 — not as an invented rule.
- **Any operation that edits or deletes a payment** (D12: immutable). The path
  answers 405 for those methods by the contract's absence, asserted in P6.
- **Revenue aggregation** (the payment counts and sums the report reads are
  S5.4's, SMS-35).
- **Concurrency.** One request at a time in the suite; the uniqueness constraint
  is the backstop for two simultaneous writes.

### 1.3 Shared changes

- `src/db/migrations/0007_*.sql` — generated from it.

The new file the manifest names is `src/modules/appointments/payments.ts`; the

## 4. Causality

```
$ npm run check:test-first
check-test-first: 19/19 entries pass.
```

The manifest entry is added in the stage's `test:` commit;
`src/modules/appointments/payments.ts` does not exist at that commit, so the
checker proves the file was added after the test (plan §6.2, D-17). The five
files under `touches` exist before the stage and are exempt by construction.

The same limitation as before: causality is proven for the file, not for each
behaviour.

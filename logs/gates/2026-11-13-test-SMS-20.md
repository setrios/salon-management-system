### 1.1 What "verified" means for each

- **NF-006** is a negative claim with three positive sides: the administrator, the
  owning master and the token holder each see the name and phone; another master's
  calendar does not contain the record at all (REQ-F-013 scopes M1 to the JWT
  subject), and a token that names nothing answers 404 rather than 401 or 403, so
  the refusal says nothing about whether the token ever existed.
- **NF-007** is checked against the *contract*, not only the server: every
  parameter and every schema property in `src/contract/openapi.json` is searched
  for a location, zone, offset or UTC selector. A control that existed but was
  undocumented would still be a violation, and the contract is the whole of the
  API's surface (D-5). N3b adds the positive half: the instants that leave the
  server carry the salon's offset.
- **NF-005 and NF-009 are absence constraints**, so they are read rather than
  called: the sources, the migrations and `package.json`. An API call can only
  show what is absent at the moment it is asked; reading the artifact's inputs is
  what makes "no purge job" and "no gateway" checkable. The scan strips comments
  first, so prose that uses the words ("the archive of what was booked") cannot
  pass or fail the check.

### 1.2 Characterisation is marked, not disguised

N1 and N6 pass on the behaviour S2.2/S2.3 and S2.1 delivered; they are
**characterisation**, and the gate says so rather than presenting them as new RED
evidence (the precedent is `§8.2` item 5 of the plan for SMS-44). Their one-line
form is deliberate: the acceptance record should be readable on its own without
claiming again what two other gates already signed.

**What was genuinely uncertain in this stage** was the three claims that failed on
first write (§3). None of them was an implementation defect — the tests encoded
three wrong assumptions, and each correction is recorded.

### 1.3 No manifest entry (D-17)

SMS-20 has no implementation file, so it adds **no `tests/manifest.json` entry**;
`npm run check:test-first` stays at 20/20 and the checker has nothing to say about
this file. The precedent is SMS-44's structural test, which the plan also excludes.

## 3. First run — what was wrong, and where

```
$ npx vitest run tests/acceptance/nfr.test.ts
     × N2 gives the client’s name and phone to the administrator, the owning master and the token holder only
     × N4 contains no purge job, retention schedule or destructive SQL
     × N6 accepts only start times on a 30-minute boundary (REQ-NF-008)
     ✓ N1, N3, N3b, N5

 AssertionError: expected 200 to be 404
 AssertionError: expected [ Array(1) ] to deeply equal []
 AssertionError: expected 'BUSINESS_RULE_VIOLATION' to be 'VALIDATION_ERROR'
      Tests  3 failed | 4 passed (7)
```

Three corrections, all in the test, none in the application:

1. **N2** asserted that P9 without a token answers 404. P9 is public but
   token-addressed (REQ-NF-001): the token *is* the credential, so the request was
   a valid one with a wrong token, which P9 correctly answers 200. The assertion
   was removed; the 404 claim moved to the unknown-token request, where it belongs.
2. **N4** matched the word `archive` in a doc comment ("the archive of what was
   booked is the service lines"). The scan now strips comments before matching, so
   it reads code rather than prose.
3. **N6** expected `VALIDATION_ERROR` for an off-grid `startAt`. S2.1's D3 makes it
   `BUSINESS_RULE_VIOLATION` — the body is well formed and the *slot rule* is what
   it breaks — which is what the server answers. The expectation was corrected to
   the documented code.

The third one is worth naming: it is the kind of assumption an acceptance test is
prone to, and had it been "fixed" in the application instead, the acceptance test
would have rewritten a rule that a signed gate already decided.

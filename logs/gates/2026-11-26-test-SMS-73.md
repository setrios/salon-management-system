## 1. The defect, and what it caused

M3 uses `<input type="time">`. A browser draws that control in its own locale,
so under `en-US` it shows "09:00 AM – 06:00 PM", whatever U-4 says. The
interface cannot choose the format of a native control.

The consequence reported in the same check — "No free time on this date" for
every date, an empty master list, **Book** never enabled — is the same chain,
not three defects. A reproduction in this repository (M3 → weekly hours
entered through the interface → C1) shows the slots 09:00…17:00 correctly when
a weekly rule is saved; with no saved rule, P7 answers no slot on any date, so
C1 has no time to offer, hence no master to list, hence nothing to book. The
developer's own database was checked: `SELECT … FROM availability_weekly` returned
**0 rows** — no weekly rule had been saved, which confirms the chain. A rule
typed in the 12-hour picker with an end before its start is refused by M4, so
the defect of §1 is the likely way no rule got saved.

## 2. The tests (browser locale `en-US`)

| Case | Asserts | Red run |
|---|---|---|
| T1 | every **From** / **To** field of M3 has the placeholder `HH:MM` | `Expected: "HH:MM"`, `Received: ""` |
| T2 | `09:00`–`18:30` typed in a weekly row is stored as `09:00` / `18:30` (M3 → API) | passes — the guard the fix must keep |
| T3 | `9:00 AM` / `6:30 PM` mark **To** `aria-invalid="true"` (K7), no **Saved.**, the stored rules unchanged | `Expected: "true"`, `Received: ""` |

## 3. Planned fix

Replace the native time control in M3 by a text field: `inputmode="numeric"`,
placeholder `HH:MM`, a suggestion list of the 30-minute times `00:00…23:30`
(REQ-NF-008 schedules on half hours), and a check before M4: a value that is not
`HH:MM` in 24 hours marks its field (K7) with **Use the 24-hour format, for
example 09:00 or 18:30.** and nothing is sent. The server's own validation
(`WeeklyRule`/`DateRule` patterns) is unchanged.

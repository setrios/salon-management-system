## 1. Scope

Three read-only operations, none of which writes anything:

| Operation | Method and path | Answer |
|---|---|---|
| R28 `getRevenueReport` | `GET /admin/reports/revenue` | `RevenueReport` — total, count, per-method breakdown |
| R29 `getPopularServicesReport` | `GET /admin/reports/popular-services` | `PopularServicesReport` — ranked services |
| R30 `getStockLevelsReport` | `GET /admin/reports/stock-levels` | `StockLevelsReport` — a point-in-time snapshot |

The requirements are REQ-F-022 (revenue for a preset or a custom window),
REQ-F-032 (popular services ranked by booking count, tie-broken by name, D16) and
REQ-F-033 (stock levels, no period).

### 1.1 The inventory

| # | Decision | Where it is asserted |
|---|---|---|
| Q1 | An **unrecognised `period` value is 422 `INVALID_PERIOD`**, not 400. `error-model.md` §3 names exactly this case in the `INVALID_PERIOD` row, so the operation applies the contract's enum itself instead of letting the generic query validator answer `MALFORMED_REQUEST`. | R4, R8 |
| Q2 | **Revenue counts only payments with `status: paid`**, by `recordedAt`. An `unpaid` payment is a record of money owed, not money received; `totalAmount`, `paymentsCount` and `byMethod` all read the same rows. | R1 |
| Q3 | **Popular services count every appointment in the window, whatever its status**, by `startAt`. REQ-F-032 names no status, so excluding cancelled bookings would be a rule the SRS does not state. R6 asserts the cancelled appointment counts, so the reading is visible rather than implicit. | R6 |
| Q4 | `PopularServiceItem.name` is the **current** service name from `services`, not the booking snapshot: the row is a ranking of a service, not a record of one booking (REQ-NF-005 governs the appointment's own body, not the catalogue's label). | R6, R7 |
| R1 | The **window** is inclusive of both endpoints, in salon dates. `day` = today, `week` = ISO Monday–Sunday containing today, `month` = the calendar month of today; all resolved against the application's clock in `Europe/Kyiv`. A custom range is used as given, and the echoed `period` is `custom`. | R1, R2, R7 |
| R2 | **`byMethod` lists only methods that occur**, in the contract's example order (cash, card), and an empty window gives `[]` — not a zero row for each method. | R1, R3 |
| R3 | **The stock snapshot includes inactive materials** and orders items by name; `asOf` is the request's clock instant in the salon offset. A material's quantity is the balance the ledger has produced, not `initialStockQuantity`. | R9 |
| R4 | **A period parameter on R30 is ignored, not refused** (REQ-F-033: no period applies). The contract declares no 422 for R30, and D17 makes unknown query parameters ignorable. | R10 |
| R5 | An invalid **calendar date** (`2026-02-30`, `2026-11-31`, text) is 400 `MALFORMED_REQUEST`: it is a malformed query parameter, not a period conflict. The 400 is declared for all three operations. | R5, R8 |

### 1.2 What the stage does not deliver

- **Any write.** The three operations are reads; no table is created.
- **Pagination.** The contract declares none for any of them: the ranking and the
  stock list are returned whole. A salon's service catalogue and material list
  are bounded by the domain, not by a page size.
- **`INVALID_PERIOD` on R30.** R30 declares no 422; a period parameter is ignored
  (R4) rather than refused.
- **Aggregation by currency.** `Money` admits only `UAH`, so the sums have one
  currency by construction; a second one would need a schema change first.

### 1.3 Shared changes

- `src/routes.ts` — mounts the three routes.
- `src/lib/time.ts` — `formatCalendarDate`, the inverse of `parseCalendarDate`,
  needed to echo resolved preset dates as `YYYY-MM-DD`.

New files: `src/modules/reports/period.ts` (window resolution), `service.ts`

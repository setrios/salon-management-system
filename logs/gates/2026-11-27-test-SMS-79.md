## 1. What changes, and what does not

| | Before (U-4, SMS-73) | After (U-4 amended) |
|---|---|---|
| Times shown (slot buttons, **When**, calendar, lists) | always `10:00`, 24-hour | the browser's hour cycle: `10:00 AM` (12-hour) or `10:00` (24-hour) |
| M3 **From** / **To** | a text field, `HH:MM`, 12-hour input refused | the browser's own time control |
| An end not after its start in M3 | refused by the server (M4, 422) | refused in the interface, marked (K7), nothing sent |
| Language | English | **English still** (REQ-NF-003): only the hour cycle is taken from the browser, not its language — a Korean browser does not get "오전 10:00" |
| Clock | the salon's | the salon's still (REQ-NF-007) |
| Dates | `Mon 16 Nov 2026` | unchanged |
| The contract | `HH:MM`, instants with offsets | unchanged |

The SRS states no time format; U-4 was an interface decision, and the
developer changes it here. No addendum is needed: no requirement changes.

## 2. Why H4 belongs here

SMS-73's root cause was a master who saved no working hours: with the
12-hour picker, an end before the start was refused by the server and nothing
was stored, which led to "No free time" on every date. Returning to the
browser's picker without guarding that case would reopen the chain; H4 makes
the interface refuse it, with a sentence, before anything is sent.

## 5. Planned implementation

`src/web/format.ts`: `formatTime` keeps the salon's wall clock from the
contract's instant and renders it with `Intl.DateTimeFormat` in English
(`en-US` for a 12-hour browser, `en-GB` for a 24-hour one), the cycle read once
from the browser (`resolvedOptions().hourCycle`). `src/web/dom.ts`: `timeInput`
returns `type="time"` with a 30-minute `step`. `src/web/screens/master.ts`: the
check before **Save** compares each row's **From** and **To**. The user guide
and the README are updated; `check:user-guide` must stay at 0 missing.

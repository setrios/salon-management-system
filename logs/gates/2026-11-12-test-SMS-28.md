### 1.1 CL-11 — the past start, one rule, two operations

CL-11 (`spec/api/clarifications.md`) decides: a requested `startAt` **earlier
than or equal to** the injected clock is 422 `BUSINESS_RULE_VIOLATION` on P8 and
P11. The boundary is `<=`, not `<`: with `<`, booking at 09:00 when it is 09:00
would be allowed — a client booking a slot that has already begun.

The rule lives **once**, in `rules.ts` (`startInPast`), beside `serviceRejection`
and `offBoundary`, which P8 already imports. P8's handler and P11's handler both
call it; neither restates it. The tests are on both operations:

- **P8** — B1 (08:30, past, inside a free window) and B2 (09:00, exactly now)
  are 422; B3 (09:30, the first future start) is 201.
- **P11** — R11 (08:30 on the same Thursday) is 422.

This closes **G2 register row 4**. The row's deadline was "before step 7"; the
rule is implemented and tested in S3.1, before validation.

### 1.2 CL-12 — the example and the catalog

P11 declares 409 through the `SlotUnavailable` response object (example
`SLOT_UNAVAILABLE`) and 422 through `ValidationFailed` (example
`VALIDATION_ERROR`), while `error-model.md` §3 assigns P11
`INVALID_STATE_TRANSITION` and `BUSINESS_RULE_VIOLATION`. The statuses are
declared; the examples show other codes.

CL-12 records the disposition: **the catalog is normative for the code; the
example is illustrative.** The contract is not edited. R5 and R6 assert 409
`INVALID_STATE_TRANSITION`; R11 asserts 422 `BUSINESS_RULE_VIOLATION`. Both are
schema-valid `Problem` bodies, which is why the tests validate the body against
`Problem` rather than against the example.

### 1.3 B3 — a guard, not a proof

B3 (09:30 → 201) is **green before and after** the implementation. It asserts
behaviour P8 already has: a future start inside the window is accepted. It is
not a RED failure and not a defect. It exists so that a rule which refuses every
Thursday start cannot pass B1 and B2. The gate counts it as a guard, not as
evidence that the past rule works.

## 3. The order of P11's checks

The handler decides in this order, and the order is part of the design:

1. **The token** — 404 when it names nothing. Without a record there is nothing
   to decide.
2. **The state** — 409 `INVALID_STATE_TRANSITION` for `cancelled` or
   `completed`. A record that cannot be edited answers 409 whatever the body
   says; checking the body first would answer 422 for a request refused for a
   stronger reason.
3. **The past** — 422 `BUSINESS_RULE_VIOLATION` for `startAt <= now`. This is a
   property of the body, like P8's boundary check (D3), and it must precede the
   slot check: a past start inside a free window is 422, not 409. The body is
   wrong; the calendar is not.
4. **The master** — 422 when a supplied `masterId` names a master who is not
   bookable (inactive, or not role `master`). P8's rule (D4), applied to the new
   master.
5. **The coverage** — 422 when the new master does not offer every service of
   the record. Also a body fault.
6. **The slot** — 409 `SLOT_UNAVAILABLE` when the block is outside availability
   or overlaps another appointment. This is the only check whose answer can
   change between the check and the write, so it is the only one inside the
   transaction and under the advisory lock on `master_id` (D2).

The two 409s bracket the 422s: the state 409 is about the record, the slot 409
is about the calendar, and everything between is the body's fault. The
re-pricing (G8) happens after coverage, because the price comes from the new
master's links, which the coverage check reads anyway.

| # | Decision | Alternative rejected |

| G1 | `startAt <= now` → 422 on P8 and P11, one rule in `rules.ts` | `<` would allow a start that has already begun; two copies would drift |

| G3 | The service set and duration are the record's | re-reading the services would let a reschedule change what was booked |
| G4 | A new master must be bookable and offer every service, else 422 | 404 is outside P11's declared set for a body fault; 409 would invite a retry |
| G5 | P8's availability check, under the same advisory lock | a check outside the lock is stale by construction (D2) |
| G6 | One `reschedule` row per successful reschedule, no unique index | a unique index would forbid the second reschedule (REQ-F-007) |
| G7 | Reminders computed on read; recalculation and reactivation are automatic | storing them would duplicate D6 and need a migration |
| G8 | A master change re-prices from the new master's links | keeping the old snapshot would show a price the new master does not charge |

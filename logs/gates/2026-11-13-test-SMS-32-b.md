## 1. Scope

S5.1b delivers the three operations that act on one existing appointment:

| Operation | Method and path | What it does |
|---|---|---|
| R21 `updateAppointmentAdmin` | `PATCH /admin/appointments/{appointmentId}` | edits time, master, service set and/or client; recalculates the block, the price and the reminders; one client reschedule SMS |
| R22 `cancelAppointmentAdmin` | `POST /admin/appointments/{appointmentId}/cancel` | `confirmed` → `cancelled`; the acting administrator is not self-notified |
| R23 `completeAppointment` | `POST /admin/appointments/{appointmentId}/complete` | `confirmed` → `completed`; the precondition of payment (REQ-F-027) |

All three are protected by `adminAccess` and answer `AppointmentAdmin`.

### 1.1 The inventory (K1, K3–K8, L1–L6)

The K-series is the S5.1 inventory signed in
`logs/gates/2026-11-13-test-SMS-32-a.md` §1.1; the entries below restate the ones
this stage uses and add the decisions this stage had to make. **L1 and L2 were
fixed in the implementation plan §12 before the work started; L3–L6 were decided
at this gate and are recorded here for the first time.**

**K1 — the split.** S5.1b is R21, R22, R23 and the full REQ-F-030 suite. S5.1a
closed the read-and-create half; SMS-32 closes after this stage.

**K3 — R21 has no recalculation logic of its own.** REQ-F-028: the same
`reschedule.ts` decision, the same `recalculateReminders`, the same client
`reschedule` row as P11. Only the guard (`adminAccess`) and the event `actor`
differ. This is why the new module is a caller of the existing pieces, not a
second copy of them.

**K4 — R21 with `client` alone is a correction.** No event, no recalculation,
`updatedAt` changes. REQ-F-028 names date, time and master only.

**K5 — REQ-F-030 on R21 and R22.** The acting administrator receives no
notification row; the assigned master's row is unaffected. This is the evidence
SMS-18 asked for, and it closes register row 12.

**K6 — R23 writes no event.** The event catalog is `new`, `reschedule`,
`cancellation`; completion is not in it.

**K7 — statuses are `error-model.md` §3.1.** `state.ts` already encodes the
whole table; R21/R22/R23 call it and map the result to 409 `INVALID_STATE_TRANSITION`.

**K8 — `appointmentId` that names nothing is 404.** A non-uuid value follows each
operation's declared response set: R21 declares 400, so it answers 400
`MALFORMED_REQUEST`; R22 and R23 declare 404 and no 400, so they answer 404
`NOT_FOUND`. The rule is `validate.ts`'s, not a per-operation exception.

**L1 — a master change is a reschedule.** R21 with a `masterId` that changes the
master recalculates the block against the new master's calendar, re-prices the
lines from their links (G8), recalculates the reminders and writes the client
`reschedule` row. This is also the source of R21's 409: a move within one master
cannot meet another record's block, a change of master can.

**L2 — R22 does not release reminders.** A cancelled record keeps its reminder
rows in the state they had; H5 already says they are never dispatched. The
`reminders[]` of a cancelled record is register row 10 and belongs to the
addendum (SMS-45), not here.

**L3 — R21 refuses an off-boundary `startAt` with 422.** REQ-NF-008 is mapped to
R21 in the contract and the traceability matrix; R19 and P8 answer 422
`BUSINESS_RULE_VIOLATION`, and an administrator's edit should answer like an
administrator's create. The shared P11 decision does not carry the boundary
check, so R21 adds it before the slot check. P11 keeps its current 409
`SLOT_UNAVAILABLE` for the same input — one rule, two statuses. That
inconsistency is new and goes to register row 13 (owner SMS-46, stage R), because
changing P11 is not this stage's scope.

**L4 — R21 accepts `serviceIds`.** `AppointmentPatch` declares it with
`minItems: 1`, `maxItems: 20`, and the operation declares 422, so leaving a
declared field unimplemented would push a known gap into the validation stage.
The lines are re-read from the target master's links (whether or not the master
changes), and `totalDurationMinutes`, `occupiedDurationMinutes`, `endAt` and
`totalPrice` follow from `totalsFor` (REQ-F-001, REQ-F-031). A service the target
master does not offer is 422, P8's rule. A change of the service set alone writes
**no** `reschedule` event: REQ-F-028 names date, time and master.

**L5 — a supplied `startAt` always writes the client `reschedule` row,** even to
the same time. This is the reading P11 fixed in R18 (G9) and the edit inherits
it; it keeps one rule instead of a second "did it really move" check.

**L6 — R23 leaves the reminder rows in place.** H5 makes a completed record
undispatchable; clearing the rows would erase what happened. The contract's
completion example shows `reminders: []`, but an example is illustrative (CL-12's
principle). The divergence is attached to register row 10, whose addendum
(SMS-45) already owns "what the SRS does not say about the reminders of a
terminal record".

### 1.2 What the stage does not deliver

- **A payment gate on `completed`.** R23 sets the status; enforcing REQ-F-021 on
  `POST /admin/appointments/{id}/payments` is S5.3 (SMS-34).
- **The reminder rows of a cancelled record** (L2, register row 10).
- **A consistent status for P11's off-boundary refusal** (L3, register row 13).
- **Concurrency.** The guarded update and the advisory lock are P8/P11's, already
  asserted; this stage issues one request at a time.
- **`notificationsSummary` and `payment`.** Optional in `AppointmentAdmin` (J2);
  not produced here.

### 1.3 Shared changes

The stage modifies four files that already existed: `reschedule.ts` (the request
may omit `startAt`; the decision returns the effective start), `service.ts` (one
edit write instead of the reschedule-only write, plus the R22/R23 transition),
`appointments/routes.ts` (P11 passes the new input fields) and `src/routes.ts`
(mounts `adminActionRoutes`). None of them is the new file the manifest names, so
the causality checker does not cover them (§4). If implementation shows that any
of these changes was not foreseen here, it is recorded in a separate `gate:`
commit, as in S5.1a.

### 1.4 Corrections found during GREEN (2026-11-13)

Two defects in the test file — not in the implementation — surfaced after signing,
and both are corrected in `test: correct S5.1b notification and fixture
assumptions (SMS-32)`. The gate's Decision is unchanged: the stage is still GO,
and the source of each assertion is still the one §2 names.

**1. The notification-row count was written from a wrong model.** Four assertions
(U2, X1, X2, P1) expected exactly one master row per event. S4.1 writes one row
**per enabled channel** (`sms` and `in_app`), so the master has two, and the nine
first GREEN failures of this kind were the test's fault. Those four assertions now
state the property they meant — "the master's rows stand", "the row set is the
repeat's", "the records are identical before and after" — instead of a count that
depends on the master's preferences.

**2. U5's fixture was not order-independent.** U5 booked `09:30` and grew the
block to `09:30–10:30` with the service-set patch, which overlaps U1's `10:00`
fixture; under `--sequence.shuffle` U5 can run first and U1's booking then fails
with 409. The case now books `SECOND_MONDAY 12:00`, one of the two free hours in
the file's fixtures, so any order passes. This is §14 item 11's trap — a failing
test after implementation is usually the test's own assumption — and the shuffled
run is what exposes it.

The corrected file passes 14/14 in file order and in four shuffled orders, and the
full suite passes 339/339 in file order and three shuffled orders (§6 of this
record lists the commands; the numbers are in the stage report).

## 3. RED

```
$ npx vitest run tests/api/admin-appointment-actions.test.ts
 Test Files  1 failed (1)
      Tests  14 failed (14)
   Duration  1.43s
```

All 14 cases fail because none of the three operations is mounted: every request
is answered 404 by the not-found middleware, including the cases that expect
401/403 (a route that does not exist cannot be guarded). No case passes by
accident, and the fixture calls they depend on (R19, R6, R11, M4) already exist,
so the RED is attributable to the missing operations alone.

also proves nothing for the four pre-existing files modified during
implementation (§1.3) — they are `touches`, and the RED run is the proof of
necessity for them.

## 5. What GREEN implements

1. **`src/modules/appointments/admin-actions.ts`** (new) — the three handlers,
   `adminActionRoutes(router)`, and R21's composition: load by id, resolve the
   requested service set against the target master, call `rescheduleDecision`,
   apply the boundary guard (L3), run the slot check under the advisory lock
   (D2), write, answer the staff body.
2. **`src/modules/appointments/reschedule.ts`** — the request may omit
   `startAt`, the record's own start joins `RescheduleCurrent`, and the decision
   returns the effective start; P11's behaviour is unchanged.
3. **`src/modules/appointments/service.ts`** — one write for an edit
   (`editAppointment`): optional service-set replacement, optional reminder
   recalculation, optional client reschedule row, actor; plus
   `transitionAppointmentById` for R22 and R23.
4. **`src/modules/appointments/routes.ts`** — P11 passes the new input fields.
5. **`src/routes.ts`** — mounts `adminActionRoutes(admin)`.

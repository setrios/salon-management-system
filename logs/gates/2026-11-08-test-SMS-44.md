## 1. Scope

Eight assertions over the scaffold. The test was written from the contract,
`error-model.md` and plan §8.2 — not from `src/`, so it describes required
behaviour rather than current behaviour. No implementation file was edited
before this record: `git status` at the time of the RED run showed only
`tests/api/` (new), `vitest.config.ts` (modified) and the two records.

**Temporary asymmetry, by construction.** Until S5.5 `GET /api/v1/services`
answers 404 (no router mounted) while `POST /api/v1/services` answers 405 (path
exists in the contract, method does not). 405 says the *path* exists, not that
the operation is implemented, so the two do not contradict each other.

## 4. Causal independence

**No `tests/manifest.json` entry — deliberate, per D-17.** SMS-44 creates no
implementation file; it only modifies pre-existing scaffold modules. An entry
with an empty `implementation` list is rejected by `validateEntry`, and listing
a pre-existing module under `implementation` would fail `checkEntry`. The
ordering evidence for S1.0 is therefore the RED run, not git history. The checker
does not enumerate test files, so this absence is invisible to it; it is stated
here so it is not discovered later as a gap.

```
$ npm run check:test-first
check-test-first: manifest is empty — nothing to verify (exit 0). See tests/manifest.json.
```

Test file header present and cites sources:

```
Source: spec/api/error-model.md §2, §3, §4; spec/api/openapi.yaml; plan §8, §8.2
Contract: openapi.yaml#/components/schemas/Problem
Ticket: SMS-44 (Test)
```

The header cites the contract and the plan rather than a REQ/SCN id. That is a
documented consequence of S1.0 being infrastructure, not an omission: there is
no requirement in SRS v1.3 that describes "a 405 body is a Problem". The
requirement that does apply — every error is a `Problem` with a closed code —
lives in `error-model.md`, which is part of the approved contract package.

## 6. Decisions and clarification this gate records

| ID | Decision | If rejected |
|---|---|---|
| D-18 | Passwords are stored as **scrypt** hashes from `node:crypto`, `scrypt$N$r$p$salt-base64$key-base64`, N=16384, r=8, p=1, 64-byte key. No dependency is added, because installing one is forbidden by CLAUDE.md and `bcrypt` was removed from the scaffold | `pbkdf2` would change only `hashPassword` in the fixture and the verifier in the implementation; no assertion changes |
| D-19 | The single administrator is a row of `masters` with `role = 'admin'`; masters carry `role = 'master'`. Accounts are provisioned by the administrator or out of band, never by self-registration. The table's columns are declared in plan §5.1 and `src/db/schema.ts` before the fixture writes them | A separate `admins` table or a boolean flag would change the fixture's `insert` and the plan's table list; the API shape is unaffected |

**CL-09 is a clarification, not a gate decision.** `login` declares no 422,
while `error-model.md` §3 assigns `VALIDATION_ERROR` to "every operation with a
request body"; both statements are in the approved contract, and `login` is the
only one of the 17 body-taking operations for which they disagree. The register
(`spec/api/clarifications.md`, now CLOSED — nine rows, Clarified 8 → 9) fixes the
disposition: a body violating `LoginRequest` is answered **400
`MALFORMED_REQUEST`**, because the operation's response set is closed and 422
would be an undocumented response. The contract is not changed.

The implementation rule that follows is derived from the contract, never from
the word "login": if the operation declares 422 → 422, otherwise → 400. No
`operationId` branch is permitted, so the rule stays correct for any future
operation. `middleware/validate.ts` currently answers every schema violation
with 422 and therefore needs this operation-aware rule; the generated contract
carries no response codes yet, so SMS-22 must collect them (see §7).

### 1.1 H1 — the stored row replaces D6

D6 (S2.1) computed the reminders at read time and stored nothing, because
nothing dispatched a message. S3.2 is the stage that dispatches, so the
computation is replaced by a row.

The SRS asks for a row, not a computation: REQ-F-010 says the reminder is
"recorded as skipped", SCN-11 says it is "recorded as `scheduled` for the new
time", and the `notifications` table already carries `scheduled_at`, `sent_at`
and the two `event_type` values (`0004_notifications.sql`). The contract's
`Notification.eventType` enumerates `reminder_24h` and `reminder_2h`, so a
reminder **is** a notification row, and R24 is the operation that shows it.

The row is `audience: client`, `channel: sms`, `event_type: reminder_24h` or
`reminder_2h`, `scheduled_at` = the moment, `status` = `skipped` or
`scheduled`. R1 asserts the shape; R2 and R3 assert the two skip rules of
SCN-04 and SCN-05 on the rows, not only on the computed view.

### 1.2 H3 — the read is the trigger

REQ-F-010's AC says the reminder is "`sent` at the correct time". The lab has no
scheduler and the plan does not add one, so the only trigger the system has is a
read: P9, P10, P11 and R24 dispatch the due rows before answering.

A `scheduled` row whose `scheduled_at` has passed becomes `sent` with
`sent_at` = that read's clock. R4 proves the transition on P9, R6 proves it on
R24 (no appointment read first), and R10 proves it is not repeated: the second
read leaves `sent_at` at the first read's instant.

The dispatch is a write on a read. That is the cost of having no scheduler, and
it is stated here rather than hidden: the alternative — deriving the status
without writing — would leave the row saying `scheduled` after the message was
handed to the channel, and R24 would then disagree with `reminders[]`.

### 1.3 H5 — the cancelled record (G2 register row 10)

A cancelled or completed record's reminders are **not** dispatched. R9 cancels a
record, reads it after the 24 h moment, and asserts that both rows are still
`scheduled`.

What `reminders[]` should *show* for such a record is G2 register row 10, owned
by the addendum (SMS-45). This stage does not decide it: it only refuses to
claim a message was sent for an appointment that no longer exists. The row stays
open, and §5 says so.

### 1.4 The five `reschedule.test.ts` assertions

## 3. Where the dispatch runs

The dispatch is one statement, and it is the same statement in all four places:

```
update notifications
   set status = 'sent', sent_at = <now>
 where appointment_id = <id>
   and event_type in ('reminder_24h', 'reminder_2h')
   and status = 'scheduled'
   and scheduled_at <= <now>
   and exists (select 1 from appointments a
                where a.id = <id> and a.status = 'confirmed')
```

The `exists` is H5: the record's state is part of the condition, so a cancelled
or completed record cannot be dispatched by any caller, and the rule is not
restated in four places.

The order inside a read is: **dispatch, then read the rows**. P9 and R24 read
the appointment first only to learn its id; the rows they answer with are read
after the dispatch, so the response never shows a status the dispatch has just
changed.

P11 does not dispatch: the reschedule recalculates both rows in the same
transaction, so the old moments are gone before the response is built. P10
dispatches before the cancel, because a reminder that was due while the record
was still live was sent then.

## 4. Decisions the tests are written against

| # | Decision | Alternative rejected |
|---|---|---|
| H1 | A reminder is a stored `notifications` row | computing at read time (D6) cannot say "recorded", and R24 would never show a reminder |
| H2 | The skip decision is made when `startAt` is set, and stored | deciding at read time would make a reminder's status depend on when it is read |
| H3 | A due row becomes `sent` on the next read, `sent_at` = that clock | a scheduler is infrastructure the plan does not have; deriving without writing leaves the row lying |
| H4 | A `skipped` row never becomes `sent` | "the moment has passed" is true for both, so the stored status is the only thing that separates them |
| H5 | A cancelled or completed record is not dispatched | dispatching would claim a message for an appointment that no longer exists; the shape is row 10's |
| H6 | A reschedule recalculates the two rows in place | inserting new rows would make R24 grow on every reschedule and leave the old moments in the page |

## 8. What GREEN implements

- `src/modules/notifications/reminders.ts` — new: the pure engine. The two rows
  for a `startAt` and a clock (`reminderRowsFor`), the contract's view
  (`reminderViews`), and the due predicate (`isDue`).
- `src/modules/notifications/service.ts` — the four statements: insert the two
  rows, recalculate them, dispatch the due ones, read them.
- `src/modules/appointments/service.ts` — the booking transaction inserts the
  rows; the reschedule transaction recalculates them; `findByToken` loads them.
- `src/modules/appointments/view.ts` — `reminders[]` from the rows, not from
  `startAt`.
- `src/modules/appointments/routes.ts` — P9 and P10 dispatch before answering.
- `src/modules/notifications/routes.ts` — R24 dispatches before listing.
- `src/modules/appointments/reminders.ts` — removed; its content moved to the
  notifications module, where the rows live.

Nothing else. No migration: `notifications` already carries `scheduled_at`,
`sent_at`, the two `event_type` values and the four statuses.

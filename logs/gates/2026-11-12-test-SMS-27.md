### 1.1 F1 — a repeat cancellation is 200 unchanged; 409 is for `completed`

The contract's own description of P10 (`spec/api/openapi.yaml:428–430`) says:

> Cancelling an already cancelled appointment returns the current state
> unchanged (D15). Cancelling a completed appointment is rejected.

`error-model.md:186–196` is the table that decides it, and the document calls
that table "the authority for negative scenarios SCN-07 and the state rules in
D15":

| Current status | `POST .../cancel` |
|---|---|
| `confirmed` | 200 → `cancelled` |
| `completed` | 409 `INVALID_STATE_TRANSITION` |
| `cancelled` | 200, unchanged |

`resource-model.md:165` states the same rule in one line: "`POST` actions are
idempotent in effect (D15): cancelling a cancelled appointment and completing a
completed appointment return the current state rather than an error."

**The advisor's initial formulation was wrong, and that is part of the decision
history.** The S2.3 inventory first proposed that a repeat P10 answers 409. That
was an inference from P10's declared response set (200/404/409/500) without
reading the operation's description: the 409 in that set is for `completed`, not
for a repeat. The human verified the three lines above independently and
corrected the inventory before any test was written. K2 and K3 are the two cells
of the table this stage owns; the third cell (`confirmed`) is K1.

### 1.2 F2 = (b) — `reminders[]` of a cancelled record are not changed and not asserted

SRS v1.3 does not define what happens to pending reminders when an appointment is
cancelled. The glossary (lines 403–406) defines `skipped` only for a reminder
whose scheduled time has already passed at the moment of booking or reschedule —
not for a cancellation. The contract's P10 example, however, shows a reminder
with `status: skipped` on a cancelled record, while the code computes `scheduled`
for any future reminder regardless of the appointment's status.

Plan decision D-11 (`logs/2026-11-08-implementation-plan.md:85`) settles what to
do with that gap:

> Reminder behaviour on cancellation is not asserted in tests; recorded as a
> clarification candidate, not invented. … If it must be decided, it goes
> through an addendum, not through code.

So this stage changes nothing in `reminders.ts` and asserts nothing about
`reminders[]` after cancellation. **The subject of the addendum is exactly this
disagreement: the contract's P10 example shows `skipped`, the code shows
`scheduled`, and SRS v1.3 is silent.** Closing it in a TEST-GATE would rewrite a
plan decision through a gate; it is carried to the G2 register (§5 row 10) with
owner **addendum SMS-45**.

**Alternative not taken:** (a) make a cancelled record's future reminders
`skipped`, matching the contract's example. Rejected because it contradicts the
glossary's definition of `skipped` and closes D-11 in a gate. (c) return
`reminders: []` for a cancelled record. Rejected because it erases information
the contract's example keeps.

### 1.3 F6 — `state.ts` is pure, and the ordering check proves only that file

The transition table of `error-model.md` §3.1 will live in a new module,
`src/modules/appointments/state.ts`. It contains **only** that table and a pure
function over it: no I/O, no database access, no clock, no imports from
`src/db/`. `routes.ts` and `service.ts` are only modified.

The manifest entry therefore lists `state.ts` under `implementation` and the
other files under `touches`. **`check:test-first` proves ordering only for
`state.ts`.** The P10 handler lives in the existing `routes.ts`/`service.ts`,
which existed before this ticket; for them the check proves nothing, and a
"10/10" must not be read as proof that the handler was written after the tests.
What proves the handler's ordering is the RED run (§6): the tests fail against
the tree that has no P10 route, and the `test:` commit precedes the `feat:`
commit in history.

**Alternative not taken:** put everything in the existing files. Rejected
because the manifest entry would then have no provable `implementation` path —
`check:test-first` requires a file that did not exist at the test commit — and
the entry would either fail the check or have to be weakened. The mechanism stays
strict; the new module is what makes the ordering provable for the part of the
change that can be.

**K2's whole-body comparison depends on the distance between `NOW` and
`startAt`.** K2 asserts `second.body` deep-equals `first.body`. That holds only
because the appointment is three weeks out (`FAR_MONDAY = 2026-12-07`,
`NOW = 2026-11-12`): at both 09:00 and 11:00 the 24 h and 2 h reminder moments
are still in the future, so both clocks compute `scheduled` and the bodies are
identical. If `FAR_MONDAY` were moved within 24 hours of `NOW`, the 2 h moment
would be past at 11:00 and future at 09:00, the two bodies would differ, and K2
would fail **on a correct implementation**. The dependency is on the fixture's
distance from `NOW`, not on the implementation; it is named here so that a later
change to `FAR_MONDAY` is recognised as a test defect, not an implementation
defect.

## 4. Decisions this gate records

F1–F7 are the inventory's decisions, recorded in `tdd-SMS-27.md` §5 with the
alternatives. The gate restates all seven, because each one changes what the
tests assert or what GREEN may write.

### 4.1 F1 — the two cells of the state table

A repeat cancellation is **200 with the record unchanged**; 409 is for
`completed`. The sources are §1.1. K2 and K3 are the two cells; K1 is the third.
The advisor's first formulation (repeat → 409) was wrong and was corrected before
any test was written.

### 4.2 F2 — reminders are not touched

See §1.2. `reminders.ts` is not modified, and no case asserts `reminders[]` after
cancellation. The gap is register row 10, owner addendum SMS-45.

### 4.3 F3 — `completed` is arranged out of band, and R23 replaces that write

K3 puts the record into `completed` with one `update appointments set status =
'completed' where id = $1`, because the operation that produces that state is
R23 `completeAppointment` (S5.3 / SMS-34). This is arrangement, not an assertion
about storage: K3's subject is P10's answer for such a record. **The `update` is
the direct write that R23 replaces when S5.3 lands**, and the gate names it so
that the replacement is not forgotten.

**Alternative not taken:** (a) defer K3 to SMS-34. Rejected because it leaves
P10's declared 409 unproven until S5.3. (b) implement R23 now. Rejected as out of
scope.

### 4.4 F4 — P10 takes no advisory lock

Cancellation only frees a block; it never takes one, so it cannot create a double
booking. The guarantee that a freed slot is bookable again is the partial unique
index `appointments_master_start_unique` (`where status <> 'cancelled'`), and K7
reads it end to end: P7 before, cancel, P7 after, P8 again.

**Alternative not taken:** take `pg_advisory_xact_lock(master_id)` as P8 does.
Rejected because it would serialise cancellations against bookings for no
guarantee the index does not already give.

### 4.5 F5 — a first cancellation writes `updated_at`; a repeat writes nothing

The `update` is guarded by `status = 'confirmed'`, so a second call affects zero
rows and answers the current state. K2 reads under a **later** clock (11:00
instead of 09:00), so a rewrite of `updated_at` would be visible as 11:00; with
one fixed clock, "unchanged" and "rewrote the same value" would be
indistinguishable.

### 4.6 F6 — the transition table is a pure module

See §1.3. `state.ts` holds the table of `error-model.md` §3.1 and a pure function
over it, nothing else.

### 4.7 F7 — cancellation in the past is allowed

REQ-F-006's AC says "at any time, including minutes before the appointment,
succeeds without a fee or error". P10 has no notice period to check, and
inventing one would contradict the requirement. K8 books a past start (P8 accepts
it — the open G2 register row 4) and cancels it.

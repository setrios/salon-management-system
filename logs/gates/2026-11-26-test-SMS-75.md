## 1. What happened

The developer's server logged, for every request:

```
[a198ba25-…] unhandled error: Error: Failed query: select "id", "full_name" from "masters" where …
params: master,true,100
    at NodePgPreparedQuery.queryWithCache (…/drizzle-orm/pg-core/session.js:41:15)
```

and nothing more. The reason — the migrations had not been applied (F11), so
the table did not exist — had to be inferred from the README. With the cause
in the line it would have read `relation "masters" does not exist`, and the
diagnosis would have taken one look. Lab 5 step 1 asks for a log that lets a run
be analysed; a line without its cause fails that for exactly the errors that
matter most.

## 2. The tests

`errorHandler` is mounted on a minimal Express app whose one route throws a
prepared error; `process.stderr.write` is spied on.

| Case | Asserts | Red run |
|---|---|---|
| L1 | the line has the wrapper's message **and** the cause's (`relation "masters" does not exist`) | `expected '[no-trace] unhandled error: Error: Fa…' to contain 'relation "masters" does not exist'` |
| L2 | a cause of a cause is written too, after its parent (`connection terminated` → `ECONNREFUSED …`) | `expected -1 to be greater than -1` |
| L3 | the client still gets 500 `INTERNAL_ERROR`, and neither the cause nor the SQL is in the body | passes — the guard: the fix must not leak database detail (error-model.md §4) |

## 3. Planned fix

`src/middleware/error-handler.ts`: after the stack, follow `error.cause` (up
to a fixed depth, so a cyclic chain cannot loop) and write each as
`caused by: <name>: <message>`. Only stderr changes; the response and the
JSONL access log are untouched.

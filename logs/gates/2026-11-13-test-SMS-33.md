## 1. Scope

S5.2 delivers the two operations behind REQ-F-020: the ledger of material
receipts and issues, and the stock balance that every row moves.

| Operation | Method and path | What it does |
|---|---|---|
| R25 `listMaterialTransactions` | `GET /admin/materials/{materialId}/transactions` | one page of the material's ledger, filtered by `type`, `from` and `to` |
| R26 `createMaterialTransaction` | `POST /admin/materials/{materialId}/transactions` | records a `receipt` (raises the balance) or an `issue` (lowers it); an issue above the balance is 409 |

Both are protected by `adminAccess`; both name the material in the path and
answer 404 when it does not exist.

### 1.1 The inventory (M1–M10)

### 1.2 What the stage does not deliver

- **The stock-levels report** (`GET /admin/reports/stock-levels`, S5.5/SMS-35).
- **Editing or deleting a transaction.** The contract has no such operation and
  the SRS calls the rows a ledger; the stage does not invent one.
- **Unit conversion.** A transaction's quantity is in the material's own unit
  (`MaterialTransaction.quantity`); no conversion between `l` and `ml` is
  specified anywhere.
- **A concurrency test in the suite.** Two simultaneous issues are serialised by
  the row lock (M8); the suite exercises the sequential rule (T5), and the
  control run repeats it against the built artifact.
- **Negative stock.** Refused, never stored (D13, M8).

### 1.3 Shared changes

The stage adds one table and one migration, and extends two existing modules:

- `src/db/schema.ts` — the `materialTransactions` table (new).
- `src/db/migrations/0006_*.sql` — generated from it.
- `src/modules/materials/service.ts` — the ledger read and the stock write
  (existing file, modified).
- `src/modules/materials/routes.ts` — registers nothing itself; the two
  operations live in the new `transactions.ts`, mounted from there (or from
  `src/routes.ts`).
- `src/routes.ts` — mounts the module (existing file, modified).

None of the modified files is the new file the manifest names, so the causality
checker covers only `src/modules/materials/transactions.ts` (§4).

## 4. Causality

```
$ npm run check:test-first
check-test-first: 18/18 entries pass.
```

The entry was added to `tests/manifest.json` in the stage's `test:` commit, and
`src/modules/materials/transactions.ts` does not exist at that commit: the
checker proves the file was added after the test (plan §6.2, D-17). The four
files under `touches` are exempt by construction — they exist before the stage
and the checker does not claim causality for modifications.

Limitation, stated as in the previous gates: causality is proven for the file the
manifest names, not for each behaviour. T2's `updatedAt` assertion and T4's
refusal sentence could be satisfied by a different implementation; the gate
records what was asked, and the report records what was built.

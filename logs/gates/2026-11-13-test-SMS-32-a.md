## 1. Scope

S5.1a delivers the read-and-create operations for the administrator:

| Operation | Method and path | What it does |
|---|---|---|
| R19 `createAppointmentAdmin` | `POST /admin/appointments` | creates appointment on client's behalf, client view with token, suppressed admin notification |
| R20 `listAppointmentsAdmin` | `GET /admin/appointments` | appointment schedule across all masters in staff view, filtered and paged |
| `getAppointmentAdmin` | `GET /admin/appointments/{appointmentId}` | one appointment in staff view by appointmentId |

All three operations are protected by `adminAccess`.

### 1.1 The inventory (K1–K9)

**K1 — S5.1 split.** S5.1a covers the read-and-create operations (R19, R20,
`getAppointmentAdmin`). The acting half (R21 edit, R22 cancel, R23 complete, and
the full SMS-18 suite) is S5.1b.

**K2 — R19 reuses P8's booking path.** R19 has no business rules of its own: it
calls the same path P8 uses (`offBoundary`, `serviceRejection`, `startInPast`,
advisory lock transaction with `bookedBlocks`, and 409 `SLOT_UNAVAILABLE`).

**K3 — R21 uses reschedule.ts.** S5.1b owns the reschedule recalculation logic
(REQ-F-028).

**K4 — R21 client-only amendment.** S5.1b owns the amendment path with no event.

**K5 — REQ-F-030 on R19.** The acting administrator is not self-notified:
`recordAppointmentEvent` receives `actor: 'admin'`, suppressing the admin's row
while recording the client's confirmation SMS and the assigned master's
notification.

**K6 — R23 writes no events.** S5.1b / S5.3.

**K7 — Status transitions follow state.ts.** S5.1b.

**K8 — appointmentId 404.** An `appointmentId` that names no appointment
(including a malformed or non-uuid string) answers 404 `NOT_FOUND` on
`getAppointmentAdmin`, because the operation declares 404 and declares no 400.

**K9 — R20 order is startAt then id.** The appointment schedule reads
chronologically forwards, identical to M1's ordering.

### 1.2 What the stage does not deliver

- **R21, R22, R23 and the full SMS-18 suite.** Owned by S5.1b.
- **`payment` and `notificationsSummary`.** Optional fields in `AppointmentAdmin`
  (J2); not produced here.

## 4. Causality

The entry `SMS-21 (test) → SMS-32 (implementation)` in `tests/manifest.json`
names `src/modules/appointments/admin.ts` as its single implementation file.

```
$ npm run check:test-first
PASS SMS-21 (test) → SMS-32 (implementation) tests/api/admin-appointments.test.ts

check-test-first: 16/16 entries pass.
```

Exit 0. The entry proves `src/modules/appointments/admin.ts` did not exist at the
test commit.

**Limitation:** It proves nothing for the existing files modified during
implementation (`src/modules/appointments/routes.ts`,
`src/modules/appointments/service.ts`, `src/routes.ts`), which are tracked under
`touches`. The RED run is the proof of necessity for those files.

## 5. What GREEN implements

1. **`src/modules/appointments/admin.ts`** — administrative query and loading
   helpers: `loadAppointmentAdmin`, `listAppointmentsAdminQuery`, staff representation
   mapping.
2. **`src/modules/appointments/service.ts`** — extend `createAppointment` input
   with `actor?: 'client' | 'admin'` to support REQ-F-030 notification
   suppression; generalized list query supporting optional `masterId`.
3. **`src/modules/appointments/routes.ts`** — register R19, R20, and
   `getAppointmentAdmin` handlers behind `adminAccess`, with `validateBody` and
   `validateParams`.

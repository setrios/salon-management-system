## 1. Scope

One behaviour, one new value, four contract edges:

> When an appointment is cancelled, every reminder of that appointment that is
> still `scheduled` becomes `cancelled`; a reminder already `sent`, `skipped` or
> `failed` keeps its status.

The addendum's §3 lists eight acceptance criteria; the tests are eight cases
(C1–C8) plus the amendment of the one existing assertion that spoke about this
state (R9 in `tests/api/reminders.test.ts`).

### 1.1 The order of the two gates is deliberate

Plan §8.1 puts the contract update (step 5) **before** the tests (step 6). C8
therefore passes on the first run: it validates `Reminder` and `Notification`
against the amended schemas, and the schemas were amended under the
SPEC-ADDENDUM-GATE. That is characterisation of the already-gated contract, not
evidence of the behaviour — the behaviour is C1–C7 and R9, and those are red.

The same §8.1 order is why `tsc` passes at the RED commit: the widened enums are
a contract fact before any code reads them.

### 1.2 What the stage does not deliver

- **Nothing about `notificationsSummary`** — the object is declared and unproduced
  (S5.3's N7); the addendum §4 records that it will need a `cancelled` count when
  an operation produces it.
- **No new operation, schema or response code** — the operation count stays 50 and
  the schema count 58.
- **No change to the dispatch predicate.** It already sends only `scheduled`
  rows, so "a cancelled row is never dispatched" is a consequence of C1, not a new
  branch. C5 asserts the consequence anyway, because it is the requirement's
  observable half.

- both cancellation paths in `src/modules/appointments/service.ts`.
- `src/db/schema.ts` + `0009_*.sql` — the widened check constraint.
